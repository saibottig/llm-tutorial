Wiederkehrende Aufgaben — „Tests für diesen Diff", „Ticket für diese Aufgabe" — will niemand jedes Mal neu formulieren. Bevor man sie automatisiert, entscheidet eine Unterscheidung über Kosten und Zuverlässigkeit:

| | Workflow | Agent |
| --- | --- | --- |
| Schritte | stehen im Code fest | wählt das Modell pro Runde |
| Modellrolle | erledigt einzelne Schritte | verfolgt ein Ziel bis „fertig" |
| Kosten/Zeit | planbar | Vielfaches, offen |
| Testbar | ja | schwer |

```
Workflow:  Diff holen → Testfälle vorschlagen → Code schreiben
             → Tests ausführen → bei Fehler 1× nachbessern → Ergebnis

Agent:     Ziel: „Sorge für Testabdeckung dieses Diffs."
             → Modell wählt jede Runde das nächste Tool → bis es fertig meint
```

<Callout type="merke">
Entscheidend ist nicht, was moderner ist, sondern ob die Schritte im Voraus bekannt sind. Bekannt → Workflow (billiger, schneller, testbar). Unbekannt, weil die Aufgabe erkunden muss → Agent. Der häufigste Fehler: ein Agent für etwas, das ein Workflow könnte.
</Callout>

## Vier Fragen vor jedem Agenten

1. Ist die Aufgabe wirklich offen — nicht vollständig vorab beschreibbar?
2. Rechtfertigt das Ergebnis ein Vielfaches an Token und Zeit?
3. Kann das Modell die Aufgabe überhaupt?
4. Fängt etwas Fehler ab — Tests, Review, Rollback?

Ein „nein" → einfacher bauen.

## Regeln für gute Workflows

- **Ein Zweck pro Workflow.** „Erstelle ein Ticket" ✓ — „Verwalte Projekte" ✗.
- **Beispiele statt Vorschriften.** Zwei, drei echte Ergebnisbeispiele schlagen jede Regelliste, besonders bei Formaten.
- **Kontext mitgeben, nicht abfragen lassen.** Ein Ticket-Workflow bekommt Diff, Branch und Modul — er fragt nicht danach.
- **Ausgabeformat festlegen**, wenn das Ergebnis weiterverarbeitet wird.
- **Fehlerfall definieren.** Was passiert bei unbrauchbarem Ergebnis?

<Callout type="praxis">
Spezifikation gratis: die Aufgabe drei-, viermal manuell machen und notieren, welche Informationen man jedes Mal brauchte. Diese Liste ist der Workflow. Wer direkt mit dem Prompt anfängt, vergisst die Hälfte des Kontexts.
</Callout>

## Wo Workflows in Claude Code leben

- **Skills / Slash-Commands im Repo:** `/tests-fuer-diff` statt jedes Mal ein neu getippter Absatz — versioniert, teamweit, an einer Stelle verbesserbar → [Skills](../skills/).
- **Headless in der Pipeline:** `claude -p "…"` läuft nicht-interaktiv in Bitbucket Pipelines (Review-Kommentar pro PR, nächtliche Prüfung). Verschärfte Regeln: festes Ausgabeformat, enge Permissions, hartes Budget — niemand sitzt daneben.

Die praktikabelste Form ist oft die **Zwischenform**: feste Schritte, von denen einer agentisch ist — der Test-Workflow legt den Ablauf fest, lässt dem Modell aber innerhalb von „Code schreiben" die Freiheit, Dateien nachzuschlagen.

<KeyTakeaway>
- Workflow: Schritte fest, Modell erledigt einzelne. Agent: Ziel fest, Modell wählt die Schritte.
- Schritte vorab bekannt → Workflow, fast immer: billiger, schneller, testbar.
- Vor einem Agenten vier Fragen: offen? lohnend? machbar? auffangbar?
- Workflows leben als Skills/Slash-Commands im Repo und headless in Bitbucket Pipelines.
- Beispiele schlagen Regeln; fehlender Kontext ist der häufigste Grund für schlechte Ergebnisse.
</KeyTakeaway>
