Tests für bestehenden Code sind der beste Einstieg in Claude Code — nicht als Verlegenheitslösung, sondern weil das Ergebnis **maschinell prüfbar** ist: Ein Test kompiliert und läuft grün oder nicht. Begrenzter Scope, kein Produktionscode, kleiner Schaden im Fehlerfall. ([Anwendungsfälle finden](../use-cases/) verallgemeinert diese Kriterien.)

## Der Ablauf in drei Schritten

**1. Aufgabe mit Kontext stellen.** Klasse, Methoden, erwartetes Verhalten — und auf die Besonderheit zeigen:

> Schreib Tests für `BerthAllocationService.allocate()`. Interessant ist der Fall eines Schiffs, das wegen Tiefgangsbeschränkung nur bei Hochwasser anlegen kann.

**2. Konventionen kommen aus der [CLAUDE.md](../setup/).** „JUnit 5, Mockito, AssertJ, Slices statt `@SpringBootTest`" steht einmal dort — nicht in jedem Prompt. Die Ergebnisse sehen aus wie vom Team geschrieben.

**3. Claude führt aus und bessert nach.** `./gradlew test --tests "BerthAllocationServiceTest"` — von Claude selbst, iteriert bis grün.

<Callout type="merke">
Die Verifikationsschleife ist der wichtigste Einzeltipp überhaupt: Gib dem Modell immer einen Weg, sein Ergebnis selbst zu prüfen. Ein Test, der nie gelaufen ist, ist ein Textvorschlag, kein Test.
</Callout>

## Framework-Spezifika

- **Test-Slices statt Volllast:** `@WebMvcTest` für Controller, `@DataJpaTest` für Repositories, reines Mockito für Domänenlogik. Ein hochfahrender `@SpringBootTest` macht jede Iteration minutenlang — und Claude iteriert dann seltener.
- **Mocking gezielt:** Stubs für externe Abhängigkeiten (`TidalWindowClient`), `ArgumentCaptor` an interessanten Schnittstellen. Claude neigt zu Über-Mocking von Dingen, die man echt instanziieren könnte.
- **Angular:** dasselbe Muster mit `TestBed` und Jest/Karma, `ng test` als Verifikation.

## Review-Checkliste für generierte Tests

<Callout type="korrektur">
„Grün heißt gut" — der häufigste Trugschluss. Grün heißt nur: kein Widerspruch zur aktuellen Implementierung. Ein Test, der die Implementierung nachbetet, ist grün, bricht bei jedem Refactoring und findet keinen einzigen Fehler.
</Callout>

| Frage | ✓ gut | ✗ schlecht |
| --- | --- | --- |
| Verhalten oder Implementierung? | „Tiefgang über Grenzwert → Liegeplatz abgelehnt" | „`repository.save()` wurde einmal aufgerufen" |
| Unbequeme Fälle da? | Grenzwerte, leere Listen, Zeitzonen | nur der Happy Path |
| Alles trägt etwas bei? | jeder Test prüft eine fachliche Aussage | Getter- und Konstruktor-Tests |

Fehlende unbequeme Fälle im Prompt benennen — dann kommen sie auch. Wie man Testqualität über Stichproben hinaus misst: [Evals](../evals/).

<Callout type="praxis">
Wirksamster Zuschnitt: **diff-basiert**. „Hier ist mein Branch-Diff — Tests für das geänderte Verhalten" statt „teste dieses Modul". Kleiner Context, scharfe Aufgabe, prüfbares Ergebnis.
</Callout>

<KeyTakeaway>
- Unit-Tests sind der ideale Einstieg: begrenzter Scope, maschinell prüfbar, kein Produktionscode.
- Claude muss die Tests selbst ausführen und iterieren — sonst ist es nur ein Textvorschlag.
- Konventionen in die CLAUDE.md, Slices statt Volllast — das hält die Schleife schnell.
- Grün ≠ gut: auf Verhalten statt Implementierung prüfen, unbequeme Fälle einfordern.
- Diff-basiert arbeiten statt modulweise.
</KeyTakeaway>
