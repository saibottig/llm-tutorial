Ein **Skill** ist ein Ordner mit einer Anleitung — Vorgehenswissen, das nur dann Context kostet, wenn es gebraucht wird. Kern ist eine `SKILL.md`:

```markdown
---
name: integrationstest
description: Schreibt Spring-Integrationstests nach Hausstandard. Verwenden,
  wenn Integrationstests für einen Service oder ein Repository gefragt sind.
---

# Integrationstests nach Hausstandard

1. Testcontainers für Postgres, nie H2 — Dialektunterschiede haben uns
   schon zweimal Produktionsfehler gekostet
2. Basisklasse AbstractIntegrationTest erweitern (setzt Flyway auf)
3. Testdaten über die Builder in testFixtures/, keine SQL-Inserts
```

Daneben können Skripte, Vorlagen und Beispiele liegen.

## Progressive Disclosure

Dauerhaft im Context steht nur der **Kopf** (Name + Beschreibung, wenige Dutzend Token). Der **Rumpf** (oft mehrere tausend Token) wird erst gelesen, wenn das Modell den Skill anhand der Beschreibung für passend hält. Fünfzig Skills verfügbar ≠ fünfzig Anleitungen im Context — es ist ein Inhaltsverzeichnis, dessen Kapitel bei Bedarf aufgeschlagen werden.

<Callout type="merke">
Die Beschreibung entscheidet, ob der Skill überhaupt gefunden wird. Sie muss sagen, **wann** er anzuwenden ist, nicht nur was er tut — dieselbe Regel wie bei [Tool-Beschreibungen](../tool-use/). Skill greift nicht? Erst an der Beschreibung arbeiten, nicht an der Anleitung.
</Callout>

## Skills vs. MCP

<Callout type="korrektur">
„Skills sind bereinigte MCPs" — nein. Sie lösen verschiedene Probleme; der Context-Unterschied ist Folge, nicht Zweck. Ein Skill kann kein Jira-Ticket anlegen (er beschreibt nur, wie ein gutes aussieht); ein MCP-Server kennt die Jira-API, aber nicht eure Konventionen. **Der Normalfall ist beides zusammen:** MCP liefert den Zugriff, der Skill das Vorgehen.
</Callout>

| | MCP | Skill |
| --- | --- | --- |
| Wozu | Zugriff auf Systeme | Wissen über Vorgehen |
| Form | laufender Server | Ordner mit Dateien |
| Context dauerhaft | alle Tool-Schemas | nur Name + Beschreibung |
| Braucht Netzwerk/Auth | ja | nein |
| Kann Nebenwirkungen | ja | nein |

## Wofür Skills im Team

Alles, was ihr wiederholt gleich macht und wo das Hausverfahren zählt:

- Flyway-Migrationsprozess
- Code-Review-Kriterien
- neuen Microservice nach Vorlage anlegen
- Namens- und Testkonventionen

Im Repo unter `.claude/skills/` abgelegt → automatisch teamweit verfügbar, und die [CLAUDE.md](../setup/) bleibt schlank, statt zum Handbuch anzuschwellen.

<KeyTakeaway>
- Ein Skill ist ein Ordner mit Anleitung; dauerhaft im Context stehen nur Name und Beschreibung.
- Progressive Disclosure lädt den Rumpf erst bei Bedarf — fünfzig Skills kosten fast nichts.
- Skills ≠ „aufgeräumte MCPs": MCP = Zugriff, Skill = Vorgehen; der Normalfall ist beides zusammen.
- Skill greift nicht? Beschreibung schärfen, nicht die Anleitung.
- Team-Skills in `.claude/skills/` im Repo — sie entlasten die CLAUDE.md.
</KeyTakeaway>
