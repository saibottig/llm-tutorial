Nach den ersten Wochen mit [Unit-Tests](../unit-tests/) kommt die Frage: Wofür noch? Die schlechteste Antwort ist „für alles" — sie produziert enttäuschende Versuche an ungeeigneten Aufgaben. Besser: drei Fragen vor jedem Versuch.

## Das Raster

| # | Frage | Dahinter steckt |
| --- | --- | --- |
| 1 | **Wiederholt sich die Aufgabe** — oder ist sie groß genug? | Einrichtungsaufwand muss sich über Durchläufe verteilen |
| 2 | **Ist das Ergebnis prüfbar?** | ohne Prüfweg ist gut von gut aussehend nicht unterscheidbar → [Halluzinationen](../hallucinations/) |
| 3 | **Ist der Context beschaffbar?** | steht das Wissen in Code/Ticket/Doku — oder im Kopf einer Kollegin? |

<Callout type="merke">
Zwei von drei „ja" → einen Versuch wert. Dreimal „nein" → Finger weg: Die Aufgabe bietet dem Werkzeug keine Angriffsfläche, nicht das Modell ist zu schwach.
</Callout>

## Kandidaten, die bestehen

| Anwendungsfall | Warum es funktioniert |
| --- | --- |
| Testlücken schließen | prüfbar, wiederkehrend, Context im Repo |
| Legacy-Code erklären | Claude liest schneller quer als jeder Mensch; prüfbar durch Nachlesen der genannten Stellen |
| Stacktrace-/Loganalyse | Stacktrace + Code rein, Hypothese raus; am Verhalten verifizierbar |
| Mechanische Migrationen | deprecated APIs, Versionssprünge, ein Muster über 30 Dateien; per Build/Tests prüfbar |
| Confluence-Doku aus Code | die zwei Releases hinterherhinkende Schnittstellen-Seite; Review durch Fachverantwortliche |
| Review-Vorstufe | eigenen Diff vor dem menschlichen Review prüfen lassen; hebt die Grundlinie |

## Anti-Kandidaten

| Fall | Woran es scheitert |
| --- | --- |
| Architekturentscheidungen | kein prüfbares Ergebnis; entscheidender Context (Historie, Politik) steht nirgends |
| Code, den niemand prüfen kann | Prüfweg fehlt per Definition |
| Hochspezifische Optimierungslogik (z. B. Kranplanung) | Jahre an Terminal-Erfahrung sind nicht beschaffbar; subtil Falsches fällt nicht auf |
| Einmalaufgabe mit hohem Kontextaufwand | Context beschaffen dauert länger als die Aufgabe |

## Vom Einzelfall zum Team-Workflow

Raster bestanden + dreimal bewährt → als [Skill](../skills/) oder Slash-Command festhalten ([Agentische Workflows](../agentic-workflows/)). Dann profitiert das Team, nicht nur die Entdeckerin.

<Callout type="praxis">
Überraschend wirksam in der Einführungsphase: eine Confluence-Seite, auf der jeder gefundene Fall mit zwei Sätzen und dem Prompt steht — **auch die Fehlschläge**. Sie wird schnell zur meistgelesenen Seite des Teams und erspart anderen dieselben Umwege.
</Callout>

<KeyTakeaway>
- Drei Fragen vor jedem Versuch: wiederholt sich's? prüfbar? Context beschaffbar?
- Gute Kandidaten: Testlücken, Legacy erklären, Loganalyse, Migrationen, Doku aus Code, Review-Vorstufe.
- Anti-Kandidaten: Architekturfragen, Unprüfbares, nicht beschaffbarer Fach-Context.
- Bewährtes als Skill/Slash-Command festhalten — Teamnutzen statt Einzelwissen.
- Fälle und Fehlschläge sichtbar dokumentieren: beschleunigt das Onboarding aller.
</KeyTakeaway>
