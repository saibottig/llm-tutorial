Ein Modell kann von sich aus nur Text erzeugen — keine Datei lesen, kein `./gradlew test` starten. Dass Claude Code es doch tut, ist **Tool Use**: der Mechanismus unter [MCP](../mcp/), [Skills](../skills/) und allem Agentischen.

## Der Ablauf

1. **Harness beschreibt die Werkzeuge** — Name, Beschreibung, Parameterschema pro Tool (Datei lesen, editieren, Shell).
2. **Modell fordert einen Aufruf an** — strukturiert statt als Text: „führe `bash` mit `./gradlew test --tests 'BerthAllocationServiceTest'` aus".
3. **Harness führt aus** — hier greifen die [Permissions](../setup/), nicht das Modell.
4. **Ergebnis geht zurück** — die Testausgabe wird an den Verlauf angehängt.
5. **Modell macht weiter** — antwortet oder fordert das nächste Tool an, z. B. den Edit für den roten Test.

Schritte 2–5 wiederholen sich, bis das Modell antwortet statt aufzurufen:

```
Anfrage → Modell → Tool-Aufruf? ─ja→ ausführen → Ergebnis anhängen ─┐
                        │                                           │
                        └─nein→ Antwort                              └──┘
```

Mehr ist ein „Agent" nicht: diese Schleife plus Abbruchbedingung. Klasse lesen, Test schreiben, ausführen, Fehler sehen, nachbessern = viermal durch die Schleife. Der Rest ist [Harness-Arbeit](../claude-code/).

<Callout type="merke">
**Das Modell führt nichts aus.** Es formuliert Wünsche; ob sie erfüllt werden, entscheidet das Harness nach deinen Permissions. Das ist die wichtigste Sicherheitseigenschaft des Aufbaus: Jeder Tool-Aufruf ist ein Prüfpunkt → [Prompt Injection](../prompt-injection/).
</Callout>

## Eigene Tools beschreiben

Relevant, sobald man z. B. per [MCP-Server](../mcp/) ein internes System anbindet. Das Modell entscheidet allein anhand von Name, Beschreibung und Schema — es sieht den Code nie. Die Beschreibung ist Steuerung, nicht Doku, und muss sagen, **wann** das Tool dran ist:

```json
{
  "name": "suche_vessel_call",
  "description": "Sucht eine Schiffsanmeldung nach Schiffsname oder Call-ID.
    Verwende dies bei jeder Frage zu einem konkreten Vessel Call — antworte
    nie aus dem Gedächtnis, die Anlaufdaten ändern sich laufend.",
  "input_schema": {
    "type": "object",
    "properties": {
      "suchbegriff": { "type": "string", "description": "Schiffsname oder Call-ID" }
    },
    "required": ["suchbegriff"]
  }
}
```

Regeln dazu:

- **Wenige, klar getrennte Tools** — zu viel Auswahl senkt messbar die Trefferquote.
- **Sprechende Namen** — `suche_vessel_call`, nicht `suche`.
- **Fehler komplett zurückmelden** — ein voller Stacktrace als Tool-Ergebnis ermöglicht die Nachbesserung; eine verschluckte Exception nicht.
- **Unabhängige Aufrufe parallel** — drei Dateien gleichzeitig lesen statt nacheinander.

## Der Preis

Jede Tool-Definition steht bei **jeder Anfrage** im Context, auch ungenutzt — zehn Tools mit ausführlichen Schemas kosten schnell mehrere tausend Token pro Aufruf. Das nächste Kapitel [MCP](../mcp/) macht daraus das zentrale Kostenthema.

<KeyTakeaway>
- Tool Use = Modell fordert an, Harness führt aus; jede Dateiänderung und jeder Testlauf in Claude Code läuft darüber.
- Ein Agent ist die Tool-Schleife plus Abbruchbedingung — mehr nicht.
- Tool-Beschreibungen sind Steuerung: sie müssen sagen, wann das Tool zu benutzen ist.
- Fehler vollständig zurückmelden — sie sind das Material der Nachbesserung.
- Jede Definition kostet Context bei jeder Anfrage, auch ungenutzt.
</KeyTakeaway>
