Eine **Halluzination** ist eine Ausgabe, die plausibel klingt und falsch ist: erfundene Quellen, nicht existierende Methoden, falsche Zahlen mit korrekt aussehender Nachkommastelle. Der Mechanismus: Das Modell wählt fortlaufend das wahrscheinlichste nächste Token — es fragt „was passt hier hin?", nicht „stimmt das?". Fehlt Wissen, entsteht kein Loch, sondern die plausibelste Fortsetzung — nach denselben Regeln erzeugt wie eine richtige Antwort und deshalb von ihr nicht zu unterscheiden.

<Callout type="merke">
Halluzinationen sind kein reparierbarer Defekt, sondern die Kehrseite der nützlichen Fähigkeit, flüssig zu ergänzen. Und: **Sicherheit im Ton sagt nichts über Richtigkeit** — eine erfundene Quellenangabe klingt genauso selbstbewusst wie eine korrekte.
</Callout>

## Risikozonen im Entwickleralltag

- **APIs und Bibliotheken:** die plausibel klingende Spring-Property, das Angular-API aus einer älteren Major-Version, die Mockito-Methode mit leicht anderem Namen
- **Konkrete Zahlen:** Versionsnummern, Jahreszahlen, Preise, Statistiken
- **Quellen und Zitate:** Titel- und Autorenformate sind leicht nachzubilden
- **Alles nach dem Trainingsstand:** ein neues Spring-Boot-Release existiert für das Modell nicht, bis die Release Notes im Context liegen
- **Nischenwissen:** je dünner das Trainingsmaterial, desto eher wird ergänzt statt gewusst

## Gegenmittel, nach Wirksamkeit

| Maßnahme | Wirkung |
| --- | --- |
| **Grounding** — Fakten mitgeben statt abfragen | kategorial besser, nicht graduell: Antworten aus beigefügtem Material halluzinieren dramatisch seltener |
| **Verifizierbar bauen** — Code kompiliert, Tests laufen, IDs laufen gegen die Datenbank | automatische Prüfung schlägt jede Ermahnung; die [Verifikationsschleife](../unit-tests/): eine halluzinierte Methode überlebt keinen Compiler-Lauf |
| **Belegpflicht** — jede Aussage an eine Stelle im Material knüpfen | macht Lücken sichtbar statt sie zu füllen |
| **Nichtwissen erlauben** — „steht nicht im Material" ist eine vollwertige Antwort | verändert das Verhalten spürbar |
| **Zweiter Blick mit frischem Context** — Ausgabe gegen Quellmaterial prüfen | findet einen guten Teil; als Selbstkritik im selben Verlauf deutlich schwächer |

<Callout type="praxis">
Bei Recherchen mit Quellenangaben: jede genannte URL tatsächlich abrufen. Erfundene Quellen fallen sofort auf — billiger und zuverlässiger als jeder Prompt-Trick.
</Callout>

<Callout type="praxis">
Fragen lassen statt raten lassen: **„Stell mir drei Rückfragen, bevor du eine
Zeile Code schreibst."** Fehlender Kontext ist die billigste Art von Erfindung,
der man zuvorkommen kann — die Rückfragen zeigen genau, welche Annahme sonst
still gefüllt worden wäre, und die Hälfte davon gehört in die
[CLAUDE.md](../setup/).
</Callout>

## Was wenig hilft

- ✗ **„Erfinde nichts" in den Prompt** — das Modell weiß nicht, dass es erfindet
- ✗ **Nach der Sicherheit fragen** — selbsteingeschätzte Konfidenz ist schwach kalibriert und selbst wieder erzeugter Text
- ✗ **Größeres Modell** — halluziniert seltener, aber überzeugender

## Die Entwurfsfrage

Für jede Stelle, an der eine Modellausgabe weiterverwendet wird: **Was passiert, wenn das frei erfunden ist?** „Nichts Schlimmes" → Grounding reicht. „Fällt niemandem auf und richtet Schaden an" → Prüfstufe einbauen. Derselbe Grundsatz wie bei [Prompt Injection](../prompt-injection/): Kontrolle gehört außerhalb des Modells.

<KeyTakeaway>
- Halluzinationen entstehen aus Wahrscheinlichkeit statt Wahrheitsprüfung — kein behebbarer Defekt.
- Sprachliche Sicherheit ist kein Signal für Richtigkeit.
- Grounding wirkt kategorial; beim Code ist die Verifikationsschleife das Gegenmittel — Compiler und Tests.
- Konfidenz-Nachfragen und Prompt-Verbote helfen wenig.
- Entwurfsfrage je Verwendungsstelle: Was passiert, wenn das erfunden ist?
</KeyTakeaway>
