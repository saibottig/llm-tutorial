In Claude Code heißt Multi-Agent: Die Hauptsitzung startet für eine Teilaufgabe einen **Sub-Agenten** mit frischem Context — etwa „durchsuche das Monorepo nach allen Verwendungen dieser Schnittstelle". Das Muster dahinter:

```
                    ┌──────────────┐
                    │ Orchestrator │
                    └──────┬───────┘
              ┌────────────┼────────────┐
              ▼            ▼            ▼
         ┌────────┐   ┌────────┐   ┌────────┐
         │ Agent  │   │ Agent  │   │ Agent  │
         │ Suche  │   │ Code   │   │ Tests  │
         └────────┘   └────────┘   └────────┘
```

Der offensichtliche Vorteil ist **Parallelisierung**. Der wichtigere wird meist übersehen:

<Callout type="korrektur">
„Multi-Agent = mehr Context Pollution, weil jeder Agent alles wissen muss" — so nicht richtig. Sub-Agenten sind primär **Context-Isolation**: Der Sub-Agent liest zwanzig Dateien, verfolgt drei Sackgassen, produziert 50.000 Token Rohmaterial — und gibt **800 Token Zusammenfassung** zurück. Alles andere bleibt in seinem Context.

Der Trade-off lautet: **mehr Tokens insgesamt, weniger Pollution im Hauptthread.** Und weil der Hauptthread die Gesamtqualität bestimmt, ist das oft ein guter Tausch.
</Callout>

## Kosten und Schutz

**Kosten:** deutlich über einem einzelnen Agenten — je nach Zuschnitt von knapper Verdopplung bis Zehnfachem und mehr. Konkrete Zahlen für den eigenen Fall: messen, nicht aus fremden Aufbauten übernehmen. Verlässlich ist nur: Es ist eine Größenordnung, keine Randnotiz.

**Häufigster Ausfall: Schleifen.** Orchestrator fragt nach, Sub-Agent liefert Unbefriedigendes, Orchestrator fragt erneut — bis Budget oder Geduld aufgebraucht sind. Schutzmaßnahmen von Anfang an einbauen:

| Maßnahme | Regel |
| --- | --- |
| Iterationslimit | harte Obergrenze pro Agent — wirksamste Einzelmaßnahme |
| Token-Budget | Obergrenze pro Aufgabe, nicht pro Aufruf |
| Tiefenbegrenzung | Sub-Agenten starten keine eigenen Sub-Agenten |
| Fortschrittsprüfung | zwei Runden ohne Neues → abbrechen |
| Zeitlimit | Wanduhrzeit als Reißleine |

## Wann es sich lohnt

- ✓ **Unabhängige Teilaufgaben:** Recherche über viele Quellen, Analyse vieler Dateien, dieselbe Prüfung auf viele Objekte
- ✓ **Viel Rohmaterial im Zwischenschritt:** Monorepo-Recherche im Sub-Agenten, nur das Fazit landet in der Sitzung, die den Code ändert
- ✗ **Abhängige Schritte:** braucht Schritt 2 das Ergebnis von Schritt 1, zahlt man den Aufschlag ohne Gegenwert
- ✗ **Aufgaben, die ein einzelner Agent schafft**

Verwandt, aber keine Orchestrierung: mehrere Claude-Code-Sitzungen in getrennten **Git-Worktrees**, jede auf eigenem Branch — die Koordination macht der Mensch, die Einsicht ist dieselbe: getrennte Aufgaben, getrennte Contexte.

<Deep title="Frameworks für eigene Multi-Agent-Systeme">
Claude Code bringt Sub-Agenten eingebaut mit — für den Teamalltag reicht das, ein zusätzliches Framework ist unnötiger Aufbau. Wer darüber hinaus baut:

- **crewAI** — rollenbasiert, zugänglich, klassischer Orchestrator-mit-Spezialisten-Aufbau
- **LangGraph** — Ablauf als Graph, mehr Kontrolle über Zustand und Verzweigungen
- **OpenAI Agents SDK** — schlanker Ansatz mit Übergaben zwischen Agenten
</Deep>

<KeyTakeaway>
- Sub-Agenten bringen Parallelisierung — und, wichtiger, Context-Isolation: Rohmaterial bleibt draußen.
- Trade-off: mehr Tokens insgesamt, weniger Pollution im Hauptthread — oft ein guter Tausch.
- Mehrkosten sind eine Größenordnung und stark zuschnittabhängig: messen statt übernehmen.
- Schleifen mit Iterationslimit, Budget und Tiefenbegrenzung von Anfang an verhindern.
- Lohnt bei unabhängigen Teilaufgaben; Worktrees sind die manuelle Variante derselben Idee.
</KeyTakeaway>
