Nach dem Absenden passiert erst eine Weile nichts, dann läuft die Antwort gleichmäßig durch. Das ist kein Implementierungsdetail — Generierung zerfällt in zwei Phasen mit verschiedenen Flaschenhälsen:

| | Prefill | Decode |
| --- | --- | --- |
| Was passiert | kompletter Prompt wird verarbeitet, füllt den [KV-Cache](../kv-cache/) | Antwort entsteht Token für Token |
| Parallelisierbar | ja — alle Prompt-Token gleichzeitig | nein — Token 5 braucht Token 4 |
| Flaschenhals | Rechenleistung (compute-bound) | Speicherbandbreite (memory-bound) |
| Bestimmt | Zeit bis zum ersten Token (TTFT) | Token pro Sekunde |

Der entscheidende Zusammenhang: Ein längerer Prompt verschiebt die Zeit bis zum ersten Token — die Ausgabegeschwindigkeit danach bleibt gleich. Die beiden Szenarien unten stellen genau das gegenüber.

<Deep title="Warum Decode bandbreitenlimitiert ist">
Für jedes einzelne Ausgabe-Token muss das Modell seine kompletten Gewichte einmal aus dem Speicher lesen: 40-GB-Modell (ein 70B in 4 Bit) → 40 GB gelesen pro Token. Die Recheneinheiten langweilen sich dabei. Deshalb können Anbieter beim Decode mehrere Anfragen fast kostenlos bündeln — die Gewichte werden ohnehin gelesen. Genau davon lebt der Betrieb großer Modelle.
</Deep>

## Was daraus folgt

- **Promptlänge wirkt nur vorn.** Doppelt so langer Prompt ≈ doppelte Wartezeit bis zum ersten Token; die Geschwindigkeit danach ändert sich nicht.
- **Streaming versteckt die Decode-Zeit.** Tokenweise Auslieferung zeigt nur die Prefill-Pause; ohne Streaming wartet man Prefill *plus* komplette Decode-Zeit.
- **Kurze Antworten sind unverhältnismäßig teuer.** Bei zehn Ausgabe-Token dominiert der Prefill komplett — mehrere Klassifikationen gehören in eine Anfrage gebündelt.
- **Lange Claude-Code-Sitzungen starten träge.** Der Prompt ist bei jeder Runde der gesamte Verlauf. [Prompt Caching](../prompt-caching/) entschärft das: Gecachtes muss im Prefill nicht neu berechnet werden.

<Callout type="praxis">
Trägheit diagnostizieren: Lange Pause vor dem ersten Zeichen → Context zu groß oder Cache greift nicht. Antwort läuft langsam durch → liegt am Modell, kürzerer Context hilft nicht.
</Callout>

<KeyTakeaway>
- Prefill verarbeitet den Prompt parallel (rechenlastig) und bestimmt die Zeit bis zum ersten Token.
- Decode erzeugt sequentiell (bandbreitenlimitiert) und bestimmt die Token pro Sekunde.
- Promptlänge wirkt auf die Wartezeit vorn, nicht auf die Ausgabegeschwindigkeit.
- Träge Sitzung? Erst klären, welche Phase schuld ist — die Gegenmittel sind verschieden.
</KeyTakeaway>
