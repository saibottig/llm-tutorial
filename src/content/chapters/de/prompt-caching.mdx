**Prompt Caching** behält den [KV-Cache](../kv-cache/) über Anfragen hinweg: Beginnen zwei Anfragen mit demselben Text, wird dieser Anfang nur einmal verarbeitet. Eine Claude-Code-Sitzung ist der Idealfall — Tools, System-Prompt, CLAUDE.md und alte Runden bleiben über dreißig Runden exakt gleich. Nur deshalb ist eine lange Sitzung bezahlbar.

## Die eine Regel

> **Der Cache greift über einen Präfix. Jede Änderung entwertet alles, was danach kommt.**

Ein einziges geändertes Zeichen an Position 100 macht alles ab Position 100 ungültig — auch völlig unveränderte Teile dahinter.

In der Demo einen oberen Block ändern: Alle Blöcke darunter werden mit ungültig, die Ersparnis bricht von ~90 % auf einstellig ein.

## Konsequenz: Stabiles nach vorn, Wechselndes nach hinten

| Ändert sich | Gehört |
| --- | --- |
| nie | ganz nach vorn |
| pro Sitzung | nach dem festen Teil |
| pro Anfrage | ans Ende |

Claude Code ordnet selbst cache-freundlich an. Dein Beitrag als Nutzer:

- **Keine [MCP-Server](../mcp/) mitten in der Sitzung** zu- oder abschalten — Tool-Definitionen stehen ganz vorn, der gesamte Sitzungscache ist weg.
- **CLAUDE.md zwischen Sitzungen ändern**, nicht mittendrin — gleicher Effekt.

## Störer-Checkliste (für eigene Workflows)

Caching fällt **still** aus — keine Fehlermeldung, nur eine hohe Rechnung. Die üblichen Verdächtigen:

- ✗ Zeitstempel im System-Prompt („Heute ist der 25.07.2026, 10:14") — der Klassiker
- ✗ Request-ID/UUID im vorderen Bereich
- ✗ Nicht-deterministische Serialisierung der Tool-Schemas (unsortiertes Dictionary)
- ✗ Wechselnde Tool-Sets zwischen Anfragen
- ✗ Modellwechsel mitten in der Sitzung — Caches gehören zu genau einem Modell

<Callout type="achtung">
Der einzige verlässliche Test ist die Abrechnung: Die API-Antwort weist aus, wie viele Token aus dem Cache gelesen wurden. Bleibt der Wert über gleichartige Anfragen bei null, ist einer der Störer am Werk.
</Callout>

<Deep title="Preise und Rentabilitätsschwelle">
| Vorgang | Preis relativ zur normalen Eingabe |
| --- | --- |
| Cache schreiben, kurze Haltbarkeit | ~1,25× |
| Cache schreiben, lange Haltbarkeit | ~2× |
| Aus dem Cache lesen | ~0,1× |

Daraus folgt: Kurze Haltbarkeit lohnt ab der **zweiten** Anfrage, lange ab der **dritten**. Ein nur einmal verwendeter Präfix zahlt drauf. Außerdem gibt es eine Mindestlänge (je nach Modell einige hundert bis wenige tausend Token) — kürzere Präfixe werden kommentarlos nicht gecacht.
</Deep>

<KeyTakeaway>
- Prompt Caching spart bis zu 90 % auf dem dominierenden Kostenblock — der Eingabe.
- Die eine Regel: Präfix-Match; jede Änderung entwertet alles danach.
- In Claude Code: MCP-Server und CLAUDE.md nicht mitten in der Sitzung ändern.
- Caching fällt still aus — die Abrechnungsfelder sind der einzige verlässliche Test.
</KeyTakeaway>
