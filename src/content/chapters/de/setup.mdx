JUnit-4-Tests statt JUnit 5, Maven statt Gradle, Klassen in Verzeichnissen, die es nicht gibt — das sind keine Modellschwächen, sondern fehlender Projektkontext. Die Lösung ist eine Datei: **`CLAUDE.md`** im Projektverzeichnis, gelesen bei jedem Sitzungsstart.

## Was hineingehört: drei Kategorien

| Kategorie | Inhalt | Beispiel |
| --- | --- | --- |
| **Befehle** | bauen, testen, prüfen | `./gradlew test --tests "…"` |
| **Konventionen** | was Claude sonst raten müsste | „AssertJ, nicht Hamcrest" |
| **Grenzen** | was nicht angefasst wird | `src/generated/**` |

So sieht das für einen unserer Services aus:

```markdown
# berth-planning-service

Spring Boot 3 / Java 21, Gradle. Teil der Vessel-Domäne.

## Befehle
- Bauen: ./gradlew build
- Einzelner Test: ./gradlew test --tests "BerthAllocationServiceTest"
- Statische Analyse: ./gradlew spotlessCheck

## Konventionen
- Tests: JUnit 5 + Mockito + AssertJ. Slices (@WebMvcTest, @DataJpaTest)
  statt @SpringBootTest, wo möglich.
- DTOs sind Records. MapStruct für Mapping, kein manuelles Umkopieren.
- Zeitstempel immer Instant, Zeitzonenlogik nur im REST-Layer.

## Nicht anfassen
- src/generated/** (aus OpenAPI generiert)
- Flyway-Migrationen — nur neue Dateien, nie ändern
```

<Callout type="merke">
Die CLAUDE.md geht bei **jeder Anfrage** als Teil des [Contexts](../context/) mit — jede Zeile kostet bei jeder Runde Tokens. Verfassung, kein Handbuch: Seltenes gehört in einen [Skill](../skills/) oder nach Confluence.
</Callout>

## Zuschnitt je Repo-Typ

- **Monorepo:** schlanke Wurzel-Datei (Build-System, übergreifende Regeln) + je eine pro Modul mit eigenen Konventionen. Claude Code liest die Dateien entlang des Pfades — Modul ergänzt Wurzel.
- **Microservices:** eine Datei pro Repo. Gemeinsamen Kern als Vorlage pflegen (z. B. in Confluence) + die drei, vier servicespezifischen Zeilen.
- **Angular-Workspace:** Testbefehle (`ng test`, Jest oder Karma), Komponenten-Konventionen (Standalone? Signals?), Ablageort geteilter UI-Bausteine.

## Permissions: abstufen statt wegklicken

In `.claude/settings.json`, eingecheckt ins Repo — dann gilt es fürs ganze Team:

| Stufe | Beispiel |
| --- | --- |
| ohne Rückfrage | `./gradlew test`, `ng test`, `git diff` |
| mit Bestätigung | `git push` |
| gesperrt | destruktive Befehle |

Zentrale Unternehmens-Policies liegen darüber; projektseitig lässt sich nur verschärfen, nicht lockern.

<Callout type="achtung">
Keine Zugangsdaten, Tokens oder internen Hostnamen in die CLAUDE.md — sie ist Teil jeder Anfrage und liegt im Repo.
</Callout>

<Callout type="praxis">
Erweiterungs-Trigger: dieselbe Korrektur zum zweiten Mal getippt. Einmal in die Datei geschrieben wirkt sie für alle künftigen Sitzungen — im Chat genau einmal.
</Callout>

<KeyTakeaway>
- CLAUDE.md = Befehle + Konventionen + Grenzen; sie ersetzt das Raten.
- Sie kostet bei jeder Anfrage Tokens: schlank halten, Seltenes auslagern.
- Monorepo: Wurzel + Modul-Dateien; Microservices: gemeinsamer Kern + Spezifika.
- Permissions in settings.json ins Repo — Testläufe frei, Push mit Bestätigung, Destruktives gesperrt.
- Wiederholte Korrektur = Signal für die Datei; Geheimnisse nie hinein.
</KeyTakeaway>
