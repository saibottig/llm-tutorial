You sharpen the CLAUDE.md or a skill, the next result looks better — change or chance? Without measurement, unanswerable. **Evals** are the answer: a fixed set of test cases with defined scoring, against which every change runs.

Why trying it out is not enough:

- **The same input produces different outputs** — one run says little.
- **Improving A often breaks B** — noticed only if B is still being tested.
- **Your own impression deceives** — you check exactly the cases you made the change for. That is not a sample.

<Callout type="merke">
Without evals you optimise on anecdotes. That works for a while, then tips over unnoticed.
</Callout>

## Getting started

1. **Collect cases, don't invent them:** ~20 real inputs from actual use; the most valuable are the ones that went wrong.
2. **Start small:** 20 cases separate effect from noise; waiting for 1,000 means never starting.
3. **Define scoring** — three kinds:

| Kind | Scoring | Fits |
| --- | --- | --- |
| exact | string/value comparison | classification, extraction, IDs |
| programmatic | code checks the output | valid JSON, tests pass |
| judged | human or model scores | summaries, tone |

The first two are cheap and stable — shift as much as possible there.

<Deep title="LLM-as-judge: the three quirks">
- **Concrete criteria over grades:** "Does the answer name all three required points?" is more stable than "rate 1–10".
- **Position effects:** comparing two answers, models systematically favour one position — swap the order and average.
- **The judge itself needs checking:** a few hand-scored cases show whether it agrees with human judgement. Uncalibrated, it reliably measures the wrong thing.
</Deep>

## Measure alongside: cost, runtime, variance

Besides quality, optimisation also shifts cost per case, runtime, error rate and **variance** — the most-forgotten one: a setup that is good on average and occasionally very bad is worse in production than one consistently slightly weaker.

<Callout type="praxis">
The biggest payoff is **regression protection**: every case that was once wrong goes into the collection — at the next rebuild it reports itself. The collection grows on its own and after months is the project's most valuable artefact.
</Callout>

## The team question: are the generated tests any good?

After months of [unit tests with Claude Code](../unit-tests/): has test quality risen — or just the count? Line coverage cannot answer that (a parroting test covers a lot and finds nothing). More honest: **mutation testing** (Java: PIT) — plants bugs in the production code and measures how many the tests notice. Applied to one module with generated and one with hand-written tests, it shows whether the generated suite checks or is merely green.

Almost everything in this tutorial is a measurable change: model choice, CLAUDE.md rework, fewer [MCP servers](../mcp/), a different [sub-agent](../multi-agent/) split, a verification stage against [hallucinations](../hallucinations/). Without evals those are guesses — with evals, decisions.

<KeyTakeaway>
- Models are not deterministic — single runs and impressions do not count as evidence.
- 20 real cases with clear scoring suffice to start; failed cases are the most valuable.
- Exact and programmatic beat judged — and the biggest payoff is regression protection.
- Measure cost, runtime and variance alongside quality.
- Quality of generated tests: mutation testing (PIT), not line coverage.
</KeyTakeaway>
