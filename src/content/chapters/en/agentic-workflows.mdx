Recurring tasks — "tests for this diff", "a ticket for this task" — nobody wants to phrase fresh every time. Before automating them, one distinction decides cost and reliability:

| | Workflow | Agent |
| --- | --- | --- |
| Steps | fixed in code | chosen by the model each round |
| Model's role | handles individual steps | pursues a goal until "done" |
| Cost/time | predictable | a multiple, open-ended |
| Testable | yes | hard |

```
Workflow:  fetch diff → propose test cases → write code
             → run tests → on failure fix once → result

Agent:     goal: "Ensure test coverage for this diff."
             → model picks the next tool each round → until it deems itself done
```

<Callout type="merke">
What matters is not which is more modern but whether the steps are known in advance. Known → workflow (cheaper, faster, testable). Unknown, because the task must explore → agent. The most common mistake: an agent for something a workflow could do.
</Callout>

## Four questions before any agent

1. Is the task genuinely open — not fully describable up front?
2. Does the outcome justify a multiple of tokens and time?
3. Can the model do the task at all?
4. Does anything catch failures — tests, review, rollback?

One "no" → build simpler.

## Rules for good workflows

- **One purpose per workflow.** "Create a ticket" ✓ — "manage projects" ✗.
- **Examples over rules.** Two or three real result examples beat any rule list, especially for formats.
- **Pass context in, don't have it asked for.** A ticket workflow receives diff, branch and module — it does not ask.
- **Fix the output format** when the result is processed further.
- **Define the failure case.** What happens with an unusable result?

<Callout type="praxis">
Free specification: do the task manually three or four times and note which information you needed each time. That list is the workflow. Starting with the prompt instead reliably forgets half the context.
</Callout>

## Where workflows live in Claude Code

- **Skills / slash commands in the repo:** `/tests-for-diff` instead of a freshly typed paragraph each time — versioned, team-wide, improvable in one place → [skills](../skills/).
- **Headless in the pipeline:** `claude -p "…"` runs non-interactively in Bitbucket Pipelines (review comment per PR, nightly check). Stricter rules apply: fixed output format, tight permissions, hard budget — nobody is sitting next to it.

The most practical shape is often the **middle form**: fixed steps, one of which is agentic — the test workflow pins the sequence but lets the model look up files freely within "write code".

<KeyTakeaway>
- Workflow: steps fixed, model handles individual ones. Agent: goal fixed, model chooses the steps.
- Steps known in advance → workflow, almost always: cheaper, faster, testable.
- Four questions before an agent: open? worth it? feasible? catchable?
- Workflows live as skills/slash commands in the repo and headless in Bitbucket Pipelines.
- Examples beat rules; missing context is the most common cause of poor results.
</KeyTakeaway>
