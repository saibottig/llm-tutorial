**Prompt caching** keeps the [KV cache](../kv-cache/) across requests: when two requests begin with the same text, that beginning is processed only once. A Claude Code session is the ideal case — tools, system prompt, CLAUDE.md and old turns stay exactly the same across thirty turns. That alone is what makes a long session affordable.

## The one rule

> **The cache matches on a prefix. Any change invalidates everything after it.**

A single changed character at position 100 invalidates everything from position 100 on — including completely unchanged parts behind it.

<CacheSimulator locale="en" />

Edit an upper block in the demo: every block below it is invalidated too, and the saving collapses from ~90 % to single digits.

## Consequence: stable to the front, changing to the back

| Changes | Belongs |
| --- | --- |
| never | right at the front |
| per session | after the fixed part |
| per request | at the end |

Claude Code arranges things cache-friendly by itself. Your contribution as a user:

- **Do not toggle [MCP servers](../mcp/) mid-session** — tool definitions sit at the very front, the whole session cache is gone.
- **Change the CLAUDE.md between sessions**, not during one — same effect.

## Cache-breaker checklist (for your own workflows)

Caching fails **silently** — no error message, just a high bill. The usual suspects:

- ✗ timestamp in the system prompt ("Today is 2026-07-25, 10:14") — the classic
- ✗ request ID/UUID near the front
- ✗ non-deterministic serialisation of tool schemas (unsorted dictionary)
- ✗ tool sets changing between requests
- ✗ model switch mid-session — caches belong to exactly one model

<Callout type="achtung">
The only reliable test is the billing data: the API response reports how many tokens were read from cache. If that value stays at zero across similar requests, one of the breakers is at work.
</Callout>

<Deep title="Prices and the break-even point">
| Operation | Price relative to normal input |
| --- | --- |
| cache write, short TTL | ~1.25× |
| cache write, long TTL | ~2× |
| cache read | ~0.1× |

It follows: short TTL pays off from the **second** request, long TTL from the **third**. A prefix used only once loses money. There is also a minimum length (a few hundred to a few thousand tokens depending on the model) — shorter prefixes are silently not cached.
</Deep>

<KeyTakeaway>
- Prompt caching saves up to 90 % on the dominant cost block — input.
- The one rule: prefix match; any change invalidates everything after it.
- In Claude Code: do not change MCP servers or the CLAUDE.md mid-session.
- Caching fails silently — the billing fields are the only reliable test.
</KeyTakeaway>
