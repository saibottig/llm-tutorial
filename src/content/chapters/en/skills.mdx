A **skill** is a folder containing an instruction — procedural knowledge that only costs context when it is used. The core is a `SKILL.md`:

```markdown
---
name: integration-test
description: Writes Spring integration tests to house standard. Use when
  integration tests for a service or repository are requested.
---

# Integration tests to house standard

1. Testcontainers with Postgres, never H2 — dialect differences have
   cost us production bugs twice already
2. Extend the AbstractIntegrationTest base class (sets up Flyway)
3. Build test data through the builders in testFixtures/, no SQL inserts
```

Scripts, templates and examples can sit alongside it.

## Progressive disclosure

Only the **header** stays permanently in context (name + description, a few dozen tokens). The **body** (often several thousand tokens) is read only once the model judges the skill relevant based on the description. Fifty skills available ≠ fifty instructions in context — it is a table of contents whose chapters are opened on demand.

<Callout type="merke">
The description decides whether the skill is found at all. It must say **when** it applies, not just what it does — the same rule as for [tool descriptions](../tool-use/). Skill not taking effect? Work on the description first, not the instruction.
</Callout>

## Skills vs. MCP

<Callout type="korrektur">
"Skills are cleaned-up MCPs" — no. They solve different problems; the context difference is a consequence, not the purpose. A skill cannot file a Jira ticket (it only describes what a good one looks like); an MCP server knows the Jira API but nothing of your conventions. **The normal case is both together:** MCP supplies access, the skill supplies the procedure.
</Callout>

| | MCP | Skill |
| --- | --- | --- |
| Purpose | access to systems | knowledge of procedure |
| Form | running server | folder of files |
| Permanently in context | all tool schemas | name + description only |
| Needs network/auth | yes | no |
| Can have side effects | yes | no |

## What team skills are for

Anything you do repeatedly the same way where the house procedure matters:

- the Flyway migration process
- code review criteria
- scaffolding a new microservice from the template
- naming and test conventions

Placed in the repo under `.claude/skills/` → automatically available team-wide, and the [CLAUDE.md](../setup/) stays lean instead of swelling into a handbook.

<KeyTakeaway>
- A skill is a folder with an instruction; only name and description stay permanently in context.
- Progressive disclosure loads the body on demand — fifty skills cost almost nothing.
- Skills ≠ "tidied-up MCPs": MCP = access, skill = procedure; the normal case is both together.
- Skill not firing? Sharpen the description, not the instruction.
- Team skills go in `.claude/skills/` in the repo — they relieve the CLAUDE.md.
</KeyTakeaway>
