The workday starts with a Jira ticket and ends with a Bitbucket PR — via [MCP](../mcp/), Claude Code reaches every station in between. Cloud: official Atlassian remote server (one-time OAuth). Data Center: community server via `claude mcp add`. What is enabled is governed by the [central configuration](../claude-code/).

## The full pass in five steps

1. **Ticket instead of retelling.** "Implement TOS-4711" is enough: Claude reads title, description, acceptance criteria and the comment discussion — more context than any verbal summary carries.
2. **Plan mode before the first edit.** Read-only: Claude reads ticket, code, modules and presents a plan. A discarded plan costs a fraction of a discarded implementation → [Working Cost-Consciously](../cost/). From a handful of affected files upward: always.
3. **Implementation with verification.** Code and tests, Claude runs build and tests itself → [Unit Tests](../unit-tests/).
4. **Branch and PR.** `feature/TOS-4711-…` per team scheme; the PR description is composed from diff + ticket.
5. **Docs along the way** — update the affected Confluence page as a proposal, not a silent automatism.

<Callout type="praxis">
The underrated step is no. 4: a good PR description needs exactly what is already in context — diff and ticket. Costs nothing extra, reviewers notice immediately.
</Callout>

## The line: read broadly, write narrowly

| Access | Risk | Recommendation |
| --- | --- | --- |
| read tickets/pages | low | allow |
| create PR | medium, visible | show before sending |
| comment tickets, edit pages | externally visible | confirm individually |

A wrong comment on the wrong ticket is public; a wrongly edited file is not.

<Callout type="achtung">
Everything read via MCP is external input: ticket texts, comments and Confluence pages can contain text that looks like an instruction — and Claude can interpret it as an order. Why that is structurally hard to prevent: [Prompt Injection](../prompt-injection/).
</Callout>

<KeyTakeaway>
- Via Atlassian MCP, Claude Code reaches Jira, Confluence and Bitbucket — from ticket to PR.
- Ticket reference beats retelling: description, acceptance criteria, comments come along.
- Plan mode before implementation — a discarded plan is cheap, a discarded implementation is not.
- Generate the PR description from diff + ticket: the underrated win.
- Read broadly, write narrowly — and everything read is external input.
</KeyTakeaway>
