A **hallucination** is an output that sounds plausible and is wrong: invented sources, non-existent methods, wrong figures with a correct-looking decimal place. The mechanism: the model repeatedly picks the most likely next token — it asks "what fits here?", not "is this true?". Where knowledge is missing, no gap appears but the most plausible continuation — produced by the same rules as a correct answer, and therefore indistinguishable from one.

<Callout type="merke">
Hallucinations are not a repairable defect but the flip side of the useful ability to fill in fluently. And: **confidence of tone says nothing about correctness** — an invented citation sounds just as assured as a correct one.
</Callout>

## Risk zones in a developer's day

- **APIs and libraries:** the plausible-sounding Spring property, the Angular API from an older major version, the Mockito method with a slightly different name
- **Specific numbers:** version numbers, years, prices, statistics
- **Sources and citations:** title and author formats are easy to imitate
- **Anything after the training cutoff:** a new Spring Boot release does not exist for the model until the release notes are in the context
- **Niche knowledge:** the thinner the training material, the more invention replaces recall

## Remedies, by effectiveness

| Measure | Effect |
| --- | --- |
| **Grounding** — supply the facts instead of querying them | categorically better, not gradually: answers from attached material hallucinate dramatically less |
| **Build verifiable** — code compiles, tests run, IDs checked against the database | automatic verification beats any admonition; the [verification loop](../unit-tests/): a hallucinated method does not survive a compiler run |
| **Require citations** — tie every claim to a place in the material | makes gaps visible instead of filling them |
| **Permit not knowing** — "not in the material" is a full answer | noticeably changes behaviour |
| **Second pass with fresh context** — check the output against the source | catches a good share; much weaker as self-criticism in the same conversation |

<Callout type="praxis">
For research with citations: actually fetch every URL given. Invented sources surface immediately — cheaper and more reliable than any prompt trick.
</Callout>

## What achieves little

- ✗ **"Don't invent anything" in the prompt** — the model does not know it is inventing
- ✗ **Asking how confident it is** — self-assessed confidence is poorly calibrated and is itself generated text
- ✗ **A bigger model** — hallucinates less often, but more convincingly

## The design question

For every place a model output is used further: **what happens if this is pure invention?** "Nothing bad" → grounding suffices. "Nobody would notice and it causes damage" → add a verification stage. The same principle as [prompt injection](../prompt-injection/): control belongs outside the model.

<KeyTakeaway>
- Hallucinations arise from probability, not truth-checking — no fixable defect.
- Linguistic confidence is no signal of correctness.
- Grounding works categorically; for code, the verification loop is the remedy — compiler and tests.
- Confidence queries and prompt prohibitions achieve little.
- Design question per usage site: what happens if this is invented?
</KeyTakeaway>
