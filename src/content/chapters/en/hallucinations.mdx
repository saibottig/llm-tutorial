A **hallucination** is an output that sounds plausible and is wrong. Invented sources, functions that do not exist, wrong figures carrying a correct-looking decimal place.

## Why it happens

A language model produces text by repeatedly choosing the most likely next token. It does not ask "is this true?" but "what fits here?".

Most of the time those coincide — in a well-trained model, true statements are also the likely ones. But when the model does not know something, no gap appears. The most plausible continuation appears instead. And it looks exactly like a correct answer, because it was produced by the same rules.

<Callout type="merke">
Hallucinations are not a defect that could be repaired. They are the flip side of the very capability that makes models useful: fluently producing plausible continuations. A model that never hallucinated would also be one that never usefully filled anything in.
</Callout>

One further point matters: **confidence of tone says nothing about correctness.** A model phrases an invented citation just as confidently as a correct one. That linguistic assurance is a stylistic property, not a signal.

## Where it shows up most

- **Specific numbers and dates** — years, version numbers, prices, statistics.
- **Sources and citations** — the classic, because title and author formats are easy to imitate.
- **Niche knowledge** — the thinner the training material, the more likely invention replaces recall.
- **APIs and libraries** — methods that *could* exist but do not: a plausible-sounding Spring configuration property, an Angular API from an older major version, a Mockito method with a slightly different name.
- **Anything after the training cutoff** — there is simply no knowledge here, only extrapolation. A new Spring Boot release is unknown to the model until you put the release notes into the context.

## What genuinely helps

**Grounding.** By far the most effective measure: give the model the facts rather than querying them. A model answering from an attached document hallucinates dramatically less than one answering from memory. The difference is not gradual but categorical.

**Require citations.** Demand that every claim be tied to a place in the supplied material. No support, no claim. That makes gaps visible instead of filling them.

**Permit not knowing.** Models would rather answer than say nothing. An explicit sentence in the prompt — that "not in the material" is a full answer — noticeably changes behaviour.

**Make it verifiable.** Where possible, build so the output can be checked: code that compiles and gets run, figures that get recomputed, IDs checked against a database. Automatic verification beats any admonition — in programming this is the verification loop from the [Unit Tests](../unit-tests/) chapter: a hallucinated method does not survive a compiler run.

**A second pass.** A separate pass checking an output against the source material catches a good share of errors — especially effective when it runs with fresh context rather than as self-criticism in the same conversation.

<Callout type="praxis">
For research with citations one simple mechanical step pays off: actually fetch every URL given. Invented sources surface immediately, and that is cheaper and more reliable than any attempt to prevent them through prompting.
</Callout>

## What helps little

- **Writing "do not make things up" in the prompt.** Changes little, because the model does not know it is making things up.
- **Asking how confident it is.** Self-reported confidence is poorly calibrated. A model can be very confidently wrong, and the self-report about it is itself generated text.
- **Larger models.** They hallucinate less often, but not never — and more convincingly when they do.

## The practical consequence

Handling this is a design question, not a prompting question. For every place a model output is used further, the question worth asking is: **what happens if this is entirely invented?**

If the answer is "nothing bad", grounding is enough. If it is "nobody will notice and it will do damage", a verification stage is needed. That is the same thought as in [Prompt Injection](../prompt-injection/): control belongs outside the model.

<KeyTakeaway>
- Hallucinations arise because models extend probability rather than check truth — they are not a fixable defect.
- Confidence of language is no indicator of correctness.
- Grounding works categorically better than any prompt wording; required citations and permitted uncertainty reinforce it.
- Automatically verifiable outputs beat any admonition — and the design question is what happens if the output is invented.
</KeyTakeaway>
