In Claude Code, multi-agent means: the main session spawns a **sub-agent** with fresh context for a sub-task — say, "search the monorepo for every use of this interface". The pattern behind it:

```
                    ┌──────────────┐
                    │ Orchestrator │
                    └──────┬───────┘
              ┌────────────┼────────────┐
              ▼            ▼            ▼
         ┌────────┐   ┌────────┐   ┌────────┐
         │ Agent  │   │ Agent  │   │ Agent  │
         │ search │   │ code   │   │ tests  │
         └────────┘   └────────┘   └────────┘
```

The obvious advantage is **parallelism**. The more important one is usually overlooked:

<Callout type="korrektur">
"Multi-agent = more context pollution, because every agent must know everything" — not quite right. Sub-agents are primarily **context isolation**: the sub-agent reads twenty files, follows three dead ends, produces 50,000 tokens of raw material — and returns an **800-token summary**. Everything else stays in its context.

The trade-off is: **more tokens overall, less pollution in the main thread.** And since the main thread determines overall quality, that is often a good trade.
</Callout>

## Cost and safeguards

**Cost:** well above a single agent — from not quite double to tenfold, depending on the design. It is an order of magnitude, not a footnote; measure your own case rather than borrowing someone else's number.

**Most common failure: loops.** Orchestrator asks again, sub-agent returns something unsatisfying, orchestrator asks again — until budget or patience runs out. Build safeguards in from the start:

| Safeguard | Rule |
| --- | --- |
| Iteration limit | hard ceiling per agent — the single most effective measure |
| Token budget | ceiling per task, not per call |
| Depth limit | sub-agents spawn no sub-agents of their own |
| Progress check | two rounds without anything new → stop |
| Time limit | wall clock as the last resort |

Where it does **not** pay: dependent steps (if step 2 needs step 1's result, the
surcharge buys nothing) and anything a single agent already handles.

Related but not orchestration: several Claude Code sessions in separate **git worktrees**, each on its own branch — the human coordinates, the insight is the same: separate tasks, separate contexts.

## Roles worth spawning

A sub-agent's value is its own window, so give it work whose *raw material* you
do not want back — and a role narrow enough to answer in a paragraph.

| Role | Task | Comes back |
| --- | --- | --- |
| Scout | "where is X used across the monorepo?" | the places, not the files |
| Adversary | "argue against this plan; name what breaks" | the objections that survived |
| Verifier | "check this diff against the ticket" | pass, or the mismatch |

The adversary is the underrated one: a second agent with fresh context and an
explicit mandate to disagree catches what the agent that wrote the plan cannot,
because it is not defending it.

<Callout type="achtung">
An adversary sub-agent is an LLM judge, with the quirks the [evals](../evals/)
chapter lists — position effects, poor calibration. It surfaces objections worth
reading; it does not rule on them.
</Callout>

<Deep title="A different model per sub-agent">
Sub-agents can run a smaller model than the main thread — planning on the
expensive one, mechanical work on the cheap one, at a factor of five between
classes → [Working Cost-Consciously](../cost/).

The mistake is doing it by switching the *main* session's model mid-task. Caches
belong to exactly one model, so the switch throws away the whole session prefix —
full price on every following turn to save a fraction on one. Delegation is what
makes the split affordable: the cheap model runs in the sub-agent's own window
and the main thread's cache stays intact.
</Deep>

<KeyTakeaway>
- Sub-agents bring parallelism — and, more importantly, context isolation: raw material stays out.
- Trade-off: more tokens overall, less pollution in the main thread — often a good trade.
- The extra cost is an order of magnitude and highly design-dependent: measure rather than borrow.
- Prevent loops with iteration limits, budgets and depth limits from the start.
- Give a sub-agent a narrow role — scout, adversary, verifier — and a cheaper model; never switch the main session's model to save.
</KeyTakeaway>
