Tests for existing code are the best entry into Claude Code — not as a makeshift, but because the result is **machine-checkable**: a test compiles and runs green or it does not. Bounded scope, no production code, small blast radius. ([Finding Use Cases](../use-cases/) generalises these criteria.)

## The workflow in three steps

**1. State the task with context.** Class, methods, expected behaviour — and point at the particulars:

> Write tests for `BerthAllocationService.allocate()`. The interesting case is a vessel that can only berth at high tide due to draught restrictions.

**2. Conventions come from the [CLAUDE.md](../setup/).** "JUnit 5, Mockito, AssertJ, slices over `@SpringBootTest`" lives there once — not in every prompt. Results look team-written.

**3. Claude runs and fixes.** `./gradlew test --tests "BerthAllocationServiceTest"` — executed by Claude itself, iterated until green.

<Callout type="merke">
The verification loop is the single most important habit there is: always give the model a way to check its own result. A test that never ran is a text suggestion, not a test.
</Callout>

## Framework specifics

- **Test slices over full boot:** `@WebMvcTest` for controllers, `@DataJpaTest` for repositories, plain Mockito for domain logic. A booting `@SpringBootTest` makes every iteration take minutes — and Claude then iterates less.
- **Mock deliberately:** stubs for external dependencies (`TidalWindowClient`), `ArgumentCaptor` at interesting boundaries. Claude tends to over-mock things that could be instantiated for real.
- **Angular:** the same pattern with `TestBed` and Jest/Karma, `ng test` as verification.

## Review checklist for generated tests

<Callout type="korrektur">
"Green means good" — the most common fallacy. Green only means: no contradiction with the current implementation. A test that parrots the implementation is green, breaks on every refactoring and finds not a single bug.
</Callout>

| Question | ✓ good | ✗ bad |
| --- | --- | --- |
| Behaviour or implementation? | "draught above limit → berth rejected" | "`repository.save()` was called once" |
| Uncomfortable cases present? | boundaries, empty lists, timezones | happy path only |
| Everything earns its place? | each test checks a domain claim | getter and constructor tests |

Name missing uncomfortable cases in the prompt — then you get them. Measuring test quality beyond spot checks: [Evals](../evals/).

<Callout type="praxis">
Most effective framing: **diff-based**. "Here is my branch diff — tests for the changed behaviour" instead of "test this module". Small context, sharp task, checkable result.
</Callout>

<KeyTakeaway>
- Unit tests are the ideal entry point: bounded scope, machine-checkable, no production code.
- Claude must run the tests itself and iterate — otherwise it is just a text suggestion.
- Conventions in the CLAUDE.md, slices over full boot — that keeps the loop fast.
- Green ≠ good: check behaviour over implementation, demand the uncomfortable cases.
- Work diff-based rather than module-wide.
