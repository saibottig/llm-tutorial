After sending, nothing happens for a while, then the answer streams through steadily. That is no implementation detail — generation splits into two phases with different bottlenecks:

| | Prefill | Decode |
| --- | --- | --- |
| What happens | whole prompt is processed, fills the [KV cache](../kv-cache/) | answer emerges token by token |
| Parallelisable | yes — all prompt tokens at once | no — token 5 needs token 4 |
| Bottleneck | compute (compute-bound) | memory bandwidth (memory-bound) |
| Determines | time to first token (TTFT) | tokens per second |

<PrefillDecode locale="en" />

The decisive relationship in the demo: a longer prompt shifts the time to first token — the output speed afterwards stays the same.

<Deep title="Why decode is bandwidth-bound">
For every single output token the model must read its complete weights from memory once: 40 GB model → 40 GB read per token. The compute units mostly idle. That is why providers can batch several requests through decode almost for free — the weights are being read anyway. Serving large models lives off exactly this.
</Deep>

## What follows

- **Prompt length only acts at the front.** Twice the prompt ≈ twice the wait for the first token; the speed afterwards does not change.
- **Streaming hides the decode time.** Token-wise delivery shows only the prefill pause; without streaming you wait prefill *plus* the whole decode time.
- **Short answers are disproportionately expensive.** With ten output tokens, prefill dominates completely — several classifications belong bundled into one request.
- **Long Claude Code sessions start sluggishly.** The prompt on every turn is the entire history. [Prompt caching](../prompt-caching/) defuses it: cached content needs no recomputation during prefill.

<Callout type="praxis">
Diagnosing sluggishness: long pause before the first character → context too large or cache not hitting. Answer streaming slowly → it is the model, a shorter context will not help.
</Callout>

<KeyTakeaway>
- Prefill processes the prompt in parallel (compute-bound) and determines time to first token.
- Decode generates sequentially (bandwidth-bound) and determines tokens per second.
- Prompt length acts on the wait at the front, not on output speed.
- Sluggish session? First establish which phase is to blame — the remedies differ.
</KeyTakeaway>
