A model can only produce text on its own — it cannot read a file or start `./gradlew test`. That Claude Code does anyway is **tool use**: the mechanism under [MCP](../mcp/), [skills](../skills/) and everything agentic.

## The flow

1. **Harness describes the tools** — name, description, parameter schema per tool (read file, edit, shell).
2. **Model requests a call** — structured, not text: "run `bash` with `./gradlew test --tests 'BerthAllocationServiceTest'`".
3. **Harness executes** — this is where [permissions](../setup/) apply, not the model.
4. **Result goes back** — the test output is appended to the history.
5. **Model continues** — answers, or requests the next tool, e.g. the edit for the red test.

Steps 2–5 repeat until the model answers instead of calling:

```
Request → Model → Tool call? ─yes→ execute → append result ─┐
                      │                                     │
                      └─no→ Answer                           └──┘
```

An "agent" is nothing more: this loop plus a stopping condition. Read class, write test, run, see failure, fix = four passes through the loop. The rest is [harness work](../claude-code/).

<Callout type="merke">
**The model executes nothing.** It formulates requests; whether they are granted is decided by the harness according to your permissions. That is the arrangement's most important security property: every tool call is a checkpoint → [Prompt Injection](../prompt-injection/).
</Callout>

## Describing your own tools

Relevant as soon as you connect an internal system, e.g. via an [MCP server](../mcp/). The model decides purely from name, description and schema — it never sees the code. The description is steering, not docs, and must say **when** the tool applies:

```json
{
  "name": "lookup_vessel_call",
  "description": "Looks up a vessel call by ship name or call ID. Use this
    for any question about a specific vessel call — never answer from
    memory, arrival data changes constantly.",
  "input_schema": {
    "type": "object",
    "properties": {
      "query": { "type": "string", "description": "Ship name or call ID" }
    },
    "required": ["query"]
  }
}
```

Rules:

- **Few, clearly separated tools** — too much choice measurably lowers the hit rate.
- **Descriptive names** — `lookup_vessel_call`, not `lookup`.
- **Report errors in full** — a complete stack trace as the tool result enables the fix; a swallowed exception does not.
- **Independent calls in parallel** — read three files at once instead of one after another.

## The price

Every tool definition sits in the context on **every request**, even unused — ten tools with detailed schemas quickly cost several thousand tokens per call. The next chapter, [MCP](../mcp/), turns this into the central cost topic.

<KeyTakeaway>
- Tool use = model requests, harness executes; every file change and test run in Claude Code goes through it.
- An agent is the tool loop plus a stopping condition — nothing more.
- Tool descriptions are steering: they must say when the tool should be used.
- Report errors in full — they are the raw material of the fix.
- Every definition costs context on every request, even unused.
</KeyTakeaway>
