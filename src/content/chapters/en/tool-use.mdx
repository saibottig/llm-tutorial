A language model can do exactly one thing on its own: produce text. It cannot read a file, run `./gradlew test`, or look anything up. When Claude Code does all of that anyway, **tool use** — also called function calling — is what is behind it. It is the mechanism [MCP](../mcp/), [skills](../skills/) and everything agentic build on.

## How it works

The flow is surprisingly plain:

1. **The harness describes the tools.** For each tool — read file, edit file, execute shell command — Claude Code sends a name, a description and a schema of the parameters.
2. **The model requests a call.** Instead of answering with text it emits structured output: "run `bash` with `./gradlew test --tests 'BerthAllocationServiceTest'`."
3. **The harness executes.** Claude Code — not the model — actually starts the command. This is where the permissions from the [Project Setup](../setup/) chapter apply.
4. **The result goes back.** The test output is appended to the conversation as a new message.
5. **The model continues.** With the result in context it answers, or requests the next tool — say, the edit that fixes the red test.

<Callout type="merke">
The point most often misunderstood: **the model executes nothing.** It only formulates a request. Whether that request is granted is decided entirely by the harness — and thus by the permissions you configured.

That is not a limitation but the single most important security property of the whole arrangement. Every tool call is a point at which you can check, filter, log or ask for confirmation. See [Prompt Injection](../prompt-injection/).
</Callout>

## The loop

Steps 2 to 5 repeat until the model stops requesting calls and answers instead. That loop is the entire core of what makes an agent:

```
Request → Model → Tool call? ─yes→ execute → append result ─┐
                      │                                     │
                      └─no→ Answer                           └──┘
```

That is all there is to it. When Claude Code reads a class, writes the test, runs it, sees the failure and fixes it — that is this loop, traversed four times. The rest — context management, permission checks, error handling — is the harness's job, see [Claude Code](../claude-code/).

## What makes a good tool description

The model decides purely from name, description and schema whether and how to use a tool. It does not see the code. The description is therefore not documentation but the actual steering mechanism. That becomes practically relevant as soon as you connect your own tools — say, through an [MCP server](../mcp/) for an internal system.

The most common mistake is to describe only *what* a tool does. Describing *when* it should be used matters at least as much:

```json
{
  "name": "lookup_vessel_call",
  "description": "Looks up a vessel call by ship name or call ID. Use this whenever a specific vessel call is requested — never answer from memory, arrival data changes constantly.",
  "input_schema": {
    "type": "object",
    "properties": {
      "query": { "type": "string", "description": "Ship name or call ID" }
    },
    "required": ["query"]
  }
}
```

Further points from practice:

- **Few, clearly separated tools** beat many overlapping ones. Given too much choice, the model measurably picks wrong more often.
- **Descriptive names.** `lookup_vessel_call` beats `lookup`.
- **Errors belong back in the loop**, not swallowed. A full stack trace as the tool result puts the model in a position to find the cause — a swallowed exception does not.
- **Several calls at once** are possible and sensible when the calls are independent of each other — reading three files in parallel instead of one after another.

## The price: context

Every tool definition sits in the context — on **every single request**, whether or not the tool is used. Ten tools with detailed schemas quickly cost several thousand tokens per call.

That is the starting point for the next chapter: [MCP](../mcp/) makes it easy to connect a great many tools — and thereby makes exactly this problem visible.

<KeyTakeaway>
- Tool use is how the model reaches the outside world — every file change and test run in Claude Code goes through it.
- The model only requests calls; the harness executes them according to your permissions. That is where the central control point lies.
- A tool description is steering, not documentation: it has to say when the tool should be used.
- Errors and stack traces belong in the tool result in full — they are the raw material of the fix.
- Every definition costs context on every request — even unused.
</KeyTakeaway>
